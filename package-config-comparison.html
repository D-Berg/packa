Packa configuration study

TOML × Lua

Two ways to describe the packages you want. TOML favors a strict, portable list. Lua favors composition and machine-aware decisions.

TOML: simple & safe Lua: flexible & reusable Best fit: use both by responsibility

01 · Same intent

One setup, two expressions

TOML

Data only
# packa.toml
version = 1

packages = [
  "git",
  "helix",
  "ripgrep",
  "zellij",
]

[install]
build_from_source = false

[[repositories]]
name = "core"
path = "/opt/packa/repos/core"
maintainer_key = "RWQ..."
mirrors = ["https://cdn.packa.dev"]

Lua

Evaluated
-- init.lua
return {
  version = 1,

  packages = {
    "git",
    "helix",
    "ripgrep",
    "zellij",
  },

  install = {
    build_from_source = false,
  },

  repositories = {{
    name = "core",
    path = "/opt/packa/repos/core",
    maintainer_key = "RWQ...",
    mirrors = { "https://cdn.packa.dev" },
  }},
}

TOML reads like a manifest

Every value is visible, validation is direct, and loading it cannot execute arbitrary behavior.

Lua reads like a tiny program

The basic form is still approachable, but it can grow into functions, loops, imports, and conditions.

03 · Real-world variation

Profiles versus logic

TOML profiles

Explicit choice
[groups.base]
packages = ["git", "ripgrep"]

[groups.desktop]
packages = ["helix", "zellij"]

[profiles.server]
groups = ["base"]

[profiles.workstation]
groups = ["base", "desktop"]

# packa apply --profile workstation

Lua conditions

Derived choice
local packages = {
  "git",
  "ripgrep",
  "helix",
}

if packa.hostname == "workstation" then
  table.insert(packages, "zellij")
end

if packa.os == "linux" then
  table.insert(packages, "strace")
end

return {
  version = 1,
  packages = packages,
}

Recommendation

Use TOML for trust. Use restricted Lua for intent.

Repository keys and mirrors benefit from a strict, data-only schema. Desired packages benefit from conditions and reusable groups across machines. Both formats can resolve into one internal Packa configuration model.
